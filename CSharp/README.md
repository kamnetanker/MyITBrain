### Создание приложения с поддержкой плагинов

**Цель:** научиться проектировать приложения так, чтобы третьи лица могли расширять их функциональность без изменения основного кода (десктоп, мобилка, игры).

**Подтемы:**
- Архитектура "Хост → Контракт → Плагин"
- Создание общего контракта (интерфейсы `IPlugin`, `ICommand` и т.п.)
- Динамическая загрузка плагинов через рефлексию
- Современная изоляция: `AssemblyLoadContext` и `AssemblyDependencyResolver`
- Интеграция с Dependency Injection (DI)
- Обнаружение плагинов через кастомные атрибуты
- Жизненный цикл плагина (загрузка → инициализация → активация → выгрузка)
- Ограничения мобильных платформ (iOS AOT, Android)
- Безопасность и песочница

### Мобильное приложение-чат для локальной сети (P2P)

**Цель:** разработать кроссплатформенное мобильное приложение для обмена сообщениями напрямую между устройствами в одной локальной сети, без центрального сервера.

**Подтемы:**
- **Обнаружение соседей (Discovery):** mDNS / Zeroconf / Bonjour[reference:7] — автоматический поиск других устройств в локальной сети.
- **Peer-to-Peer соединение:** установка прямого TCP-соединения между найденными устройствами[reference:8].
- **Альтернативный подход:** WebRTC с DataChannel для P2P-связи (обход NAT, работа через интернет)[reference:9][reference:10].
- **Обмен сообщениями:** текстовые сообщения, уведомления о статусе (онлайн/офлайн), история чата.
- **Кроссплатформенность:** .NET MAUI / Avalonia UI / Uno Platform для единого кода под Android и iOS.
- **Разрешения:** сетевые разрешения на мобильных платформах (Android, iOS)[reference:11].
- **Безопасность:** шифрование сообщений (опционально).

# 🧩 Практический проект: Универсальная панель управления сервисами (Service Manager)

> **Цель:** Создать систему, которая позволяет управлять несколькими сервисами через единую веб-панель, без необходимости писать код для каждого нового сервиса. Всё, что нужно для интеграции — JSON-манифест, описывающий API сервиса.

---

## 📌 Идея

Мы строим **Service Manager** — приложение, которое:
1. Хранит **реестр сервисов** (Service Registry) и их JSON-манифесты.
2. Предоставляет **веб-панель**, которая динамически генерирует UI на основе манифеста.
3. Позволяет **вызывать методы сервисов** через панель (прокси-запросы).
4. Умеет **регистрировать новые сервисы** без перезапуска (через API или файлы).

---

## 🧱 Компоненты системы

| Компонент | Назначение |
|-----------|------------|
| **Service Registry** | Хранит список сервисов и их манифестов. Умеет читать из папки `./Manifests`, принимать по HTTP, хранить в памяти или БД. |
| **Manifest Parser** | Парсит JSON-манифест, валидирует его схему, преобразует во внутренние объекты C#. |
| **Dynamic UI Generator** | На основе манифеста генерирует HTML-формы (или Blazor-компоненты) для каждого метода. |
| **API Proxy** | Принимает запросы от панели, формирует HTTP-запрос к целевому сервису, возвращает ответ. |
| **Service Scanner** | (Опционально) Фоновый сервис, который сканирует папку `./Manifests` и обновляет реестр при появлении новых файлов. |

# Текущая работа

## Git и GitHub workflow, CI/CD

Управление версиями - краеугольный камень production разработки. Здесь не будет классических похвальб системам контроля версий, мол ты ничего не потеряешь, можешь откатиться и т.п., основная причина для использования систем контроля версий - кооперативная разработка. Они позволяют множеству разработчиков работать над единым проектом, а современные обёртки над ними (GitLab, Gitea, GitHub) позволяют следить за Issues, комментировать, обсуждать, коллаборироваться, распространять код, строить CI/CD и это куда более важные компоненты систем контроля версий, чем принято их преподносить начинающим разработчикам.

`Git` - мейнстрим контроля версий. По сути, он занимает такую долю рынка, что остальные системы, даже если существуют - не используются. Возможно, где-то в легаси можно ещё встретить старые не портированные системы, но они постепенно вымирают. Король один - Git.

Удалённые репозитории деляться на позорные (GitLab) и пацанские (GitHub, Gitea), отличие - императивность и декларативность. Чем более позорный твой удалённый репозиторий, тем больше он нравится бизнесу и более он декларативный. Для корп декларативность - плюс, для инженера - жопа. 

В текущем конспекте будет рассматриваться связка `Gitea` + `GiteaActions` из-за полной совместимости с `Github actions`. `Gitlab CI` рассматриваться не будет, поскольку несовместим с `Github`. 

## Git - древовидная система контроля версий.

`Репозиторий` - директория в файловой системе, где находится `.git` поддиректория, содержащая файлы, описывающие репозиторий: коммиты, ветки, историю репозитория

Другие файлы - текущее состояние репозитория, т.е. конкретный набор файлов и директорий, которые относятся к активной ветке и активному коммиту.

`Коммит` - снимок репозитория, содержащий текущее на момент создания состояние файлов и директорий в репозитории

`Ветка` - история снимков, можно представить как стопку снимков состояний файлов и директорий. Несколько веток могут содержать разные истории, даже без общего "корня" (что плохо, так делать не надо, но техническая возможность есть). В нормальном репозитории все ветки коммитов сходятся в корень - момент инициализации репозитория. `Коммит` - узел этого дерева, откуда может начинаться другая ветка репозитория со своей историей изменений файлов.

В нормальном репозитории есть минимум 3 ветки: `master` - релизное состояние файлов, из которого собирается рабочая версия приложения для `production` среды (альт. назв: main, production, prod), `staging` - ветка, содержащая коммиты, в которых файлы отражают тестовую версию приложения, которая ещё не релиз, но уже тестируется (альт. назв.: `stage`, `staging`, `test`, `testing`). `develop`  - среда разработки, сюда чаще всего вносятся изменения и здесь проводятся `unit` тесты. (альт. назв.: `dev`)

Дополнительно ветки могут быть что-то вроде `dev-feature-1`, относящиеся к реализации конкретной фичи назначенным разработчиком. Или `master-hotfix-15` - быстрые исправления критических ошибок в какой-либо ветке.

Структура дерева коммитов репозитория пример:

```bash
*   (main) Merge branch staging into main (релиз)
|\
| *   (staging) Подготовка к релизу (финальные правки)
| |\
| | *   (develop) Слияние feature/login в develop
| | |\
| | | *   (feature/login) Готовая фича входа (коммит E)
| | | *   Начальная реализация входа (коммит D)
| | |/
| | *   Изменение схемы БД (коммит C)
| | *   (develop создано из staging) Добавлены базовые модели (коммит B)
| |/
| *   (staging) Ветка staging создана от main (коммит B или C)
|/
*   (init) Инициализация репозитория (корневой коммит A)
```

Условные обозначения
* \* — коммит (узел дерева).
* | / \ / / — линии, показывающие родительские связи (кто от кого произошёл).
* (main), (staging), (develop) и т.д. — имена веток (указатели на конкретные коммиты).
* (HEAD) — текущая активная ветка (в примере не показана, чтобы не усложнять).
* Коммиты читаются снизу вверх — каждый новый коммит добавляется поверх предыдущего.

В реальных проектах может быть больше веток, но описанные (`main`, `staging`, `develop`, `feature/*`, `hotfix/*`) — это минимальный набор для контролируемой разработки.

## Конфликты

Во время слияния веток может произойти конфликт, когда в ветке с которой происходит слияние есть изменения, которых нет в ветке из которой происходит слияние. В этом случае происходит ручное разрешение конфликта. Система контроля версий показывает 2 файла, файл в итоговой ветке и файл откуда происходит слияние, построчно сопоставляя их и подсвечивая изменения. В итоговом файле требуется привести его в разрешённое состояние, приняв решение, какие изменения оставить, а какие отклонить.

Вид того, как разрешается конфликт может отличаться, но обычно в итоговом файле требуется просто раскомментировать строки, содержащие слияние из исходной ветки или закомментировать то, что не требуется переносить из текущей ветки.

### Инициализация

1. Клон репозитория (обычно, когда репозиторий был создан на удалённой системе, вроде Github, GitLab или Gitea): `git clone https://url.to.remote/remote_user/remote_repo.git` - в директории, откуда была вызывана команда, будет создана директория `remote_repo`, куда будет добавлено содержимое репозитория и история веток. 
2. Инициализация репозитория: `git init` - в текущей директории будет создана директория `.git` с initial коммитом. Репозиторий создаётся пустой.

### Работа с текущими изменениями

```bash
# Посмотреть статус изменённых файлов
git status

# Добавить все изменения в индекс (подготовить к коммиту)
git add .
# или конкретный файл
git add Program.cs

# Создать коммит с сообщением
git commit -m "Добавлена валидация модели"

# Посмотреть историю коммитов
git log --oneline
```

Важно: сообщение коммита должно быть осмысленным. Писать тираду о том, в каком файле и что ты поменял не стоит, но указать "фикс валидации email" - вполне нормально

Коммиты должны быть как можно более атомарными, сделал одну микро-задачу - коммит. Коммит на каждую строчку - зря, а на микрозадачу - нормально.

### Работа с удалённым репозиторием

```bash
# Добавить удалённый репозиторий
git remote add origin https://gitea.example.com/user/repo.git

# Отправить изменения в удалённый репозиторий
```

### Работа с ветками

```bash
# Создать новую ветку и переключиться на неё
git checkout -b feature/new-validation

# Переключиться на другую ветку
git checkout main

# Показать все локальные ветки
git branch

# Показать все ветки (локальные и удалённые)
git branch -a

# Удалить локальную ветку
git branch -d feature/new-validation

# Переключиться на ветку, в которую будем сливать
git checkout main

# Слить ветку feature в текущую

```

Конфликт возникает, когда одни и те же строки файла изменены в двух разных ветках. Git не может автоматически решить, какой вариант правильный, и помечает конфликтующие участки. Их нужно исправить вручную (выбрать один вариант или скомбинировать), затем добавить файл в индекс и сделать коммит слияния

## Установка собственного удалённого репозитория

Потребуется система с `Lunix`, либо `Windows` с `WSL` и пакет `Docker` для развёртывания системы контроля версий в контейнерном окружении. 

Далее необходимо создать директорию для Gitea и создать в ней `docker-compose.yml` с примерно следующим содержимым:

```yml
services:
  gitea:
    image: gitea/gitea:latest
    container_name: gitea
    environment:
      - USER_UID=1000
      - USER_GID=1000
      - GITEA__database__DB_TYPE=sqlite3
    restart: always
    volumes:
      - ./gitea:/data
      - /etc/timezone:/etc/timezone:ro
      - /etc/localtime:/etc/localtime:ro
    ports:
      - "3000:3000"
      - "2222:22"
```

Далее в той же директории необходимо поднять Gitea:

`docker compose up -d`

эта команда запустит контейнер с Gitea в фоновом режиме и она будет доступна по адресу `http://localhost:3000`

Что здесь происходит:

- `volumes: ./gitea:/data` — данные сохраняются в папке ./gitea на хосте, чтобы не потерять их при перезапуске контейнера.
- `ports: "3000:3000"` — веб-интерфейс.
- `ports: "2222:22"` — SSH-доступ к репозиториям (порт 22 на хосте может быть занят, поэтому используем 2222).

Далее, следует открыть станицу и первый, кто зарегистрируется будет администратором этой системы. После регистрации произойдёт попадание в панель администратора.

**Важно** конфигурация Gitea хранится в `app.ini` внутри контейнера. И для взаимодейтсвия с конфигурационными файлами внутри контейнеров используется следующий алгоритм действий:

```bash
# Скопировать файл на хост
docker cp gitea:/data/gitea/conf/app.ini ./app.ini

# Отредактировать (например, включить Actions, о чём в части 2)
nano app.ini # Я рекомендую попробовать micro, он чуть лучше nano по пользовательскому опыту, но может иметь не полную поддержку.

# Скопировать обратно
docker cp ./app.ini gitea:/data/gitea/conf/app.ini

# Перезапустить Gitea
docker restart gitea
```

**push-to-create** - удобная фича, которая позволяет авторизованному пользователю создавать репозиторий путём пуша, а не через веб-панель.

В `app.ini` следует добавить в секцию `[repository]` следующее:

```yml
[repository]
ENABLE_PUSH_CREATE_USER = true
ENABLE_PUSH_CREATE_ORG = true
```

Если нужно, чтобы новосозданные репозитории были приватны:

```yml
DEFAULT_PUSH_CREATE_PRIVATE = true
```

после этого: `docker restart gitea` чтобы перезапустить сервис и применить конфигурацию.

## Рабочий пайплайн. Git Workflow. Алгоритм работы с репозиторием.

Допустим, в команде начинается работа над проектом `my-cool-app`;

**Этап 1.**

Создание проекта. Для начала `Gitea` настраивается на `push-to-create`.

```bash
# Создаём директорию проекта
mkdir my_new_app
# Инициализируем репозиторий (ВАЖНО: репозитории инициализируются в пустых директориях)
git init 
git add .
git commit -m "initial" # -m параметр позволяет задать описание коммита без открытия текстового редактора

# Добавляем удалённый репозиторий, после неё репозиторий ещё не создан, мы просто указали git на локальном компьютере куда необходимо пушить будет.
git remote add origin http://gitea.localserver.domain/username/my_new_app.git

# Пушим в мастер на origin
git push -u origin master

# Теперь только создаём сам проект
dotnet new sln -n  "MyNewApp"
dotnet new console -n "MyNewConsoleApp"
dotnet sln MyNewApp add ./MyNewConsoleApp/MyNewConsoleApp.csproj

# Структура проекта создана, теперь можно отправить его в репозиторий
git add .
git commit -m "Added dotnet solution and linked console project"
git push

# Теперь, зайдя в панель Gitea можно будет увидеть, что появился репозиторий с 2 коммитами: инициализационный и коммит с добавлением решения и проекта.
```

---

**Этап 2.**

Далее требуется создать **минимальную** структуру репозитория, которая соответствует рекомендациям по работе с версиями.

**Важно** Это не догмат, а очень важная и значимая рекомендация для работы над длительными серьёзными проектами. Для личных пет проектов или баловства, тестов или чего-то подобного, что не подразумевает длительной разработки, не подразумевает коллаборации, не подразумевает расширения и развития или является proof-of-concept применение этой структуры ведёт к managedgement-overhead и делать так не надо.

```bash
# Создаём stage ветку, для тестирование сборок
git checkout -b staging
git add .
git commit -m "add staging"
git push origin staging
# Создаём develop ветку, для тестирование сборок
git checkout -b developing
git add .
git commit -m "add developing"
git push origin developing
```

Далее работа над приложением продолжается с ветвления от ветки `develop`.

Чтобы назначить ветку по-умолчанию над которой сейчас осуществляется работа, чтобы постоянно не указывать, куда пушить, используется опция `--set-upstream`

`git push --set-upstream origin developing` - коммиты по умолчанию командой `git push` без указания ветки будут пушится в `develop`

---

**Этап 3.**

Теперь происходит работа над некоторой фичей, для чего создаётся новая ветка.

**Важно** Для личных проектов это не обязательно, но рекомендовано, если вашим личным проектом пользуются люди. Даже если ветка всего одна - `master` (`main`), ветку для разработки очередной версии приложения имеет смысл делать отдельную, чтобы люди, которые будут пользоваться и собирать ВАШ софт не столкнулись с проблемами, которые связаны с тем, что ваша сборка не очень стабильна или вовсе не собирается. В `master` ветке публичного репозитория, которым будут пользоваться другие люди должна быть та версия файлов, которая успешно собирается и не создаёт проблем с основной функциональности.

```bash
# отделяем ветку от develop для новой фичи

git checkout -b my_feature_1
git add .
git commit -m "add my_feature_1"
git push --set-upstream origin my_feature_1

# Далее после осуществления работы и коммитов в ветку, мы принимаем решение о слиянии с develop веткой

git checkout develop
git merge my_feature_1

# В соло разработке или разработке, когда никто не вносил изменения в ветку develop всё произойдёт без проблем.
# Однако, если кто-то в ветке develop произведёт изменение тех же файлов, что меняли вы в ходе своей работы, то возникнет конфликт
```

---

**Этап 4.**

Решение конфликтов.

Git сообщит о конфликте при слиянии веток, в которых есть изменения в одних и тех же файлах. Открой файл в редакторе, найди участки с маркерами:

```text
<<<<<<< HEAD
// код из main
=======
// код из feature
>>>>>>> feature/add-logging
```

Далее требуется снять маркеры с изменений, которые требуется зафиксировать в текущем коммите и сохранить файл, после повторить добавление в индекс и сделать коммит:

```bash
git add .
git commit -m "merge"
git push origin main # для примера main
```

**Этап 5.**

Периодически приходится пересматривать историю веток и искать проблемный комиит, для чего есть следующие команды.

```bash
# Показать историю в одну строку
git log --oneline
# В виде дерева
git log --graph
# --decorate добавляет читабельности
git log --graph --decorate
# Базовый древовидный вывод с указанием веток и сокращённых хешей
git log --graph --oneline --decorate

# Более детальный с датами и авторами
git log --graph --pretty=format:'%Cred%h%Creset - %s %Cgreen(%cr) %C(bold blue)<%an>%Creset' --abbrev-commit

# Показать все ветки в дереве
git log --graph --oneline --decorate --all

# Ограничить количество коммитов (например, последние 20)
git log --graph --oneline --decorate -20

# Найти коммит, который сломал тесты
git bisect start
git bisect bad HEAD
git bisect good a1b2c3d
# ... и так далее
```

## Gitea Actions и как это работает

`Workflow` - пайплайн, т.е. набор шагов, предписывающих Gitea Actions что делать с кодом в репозитории.

`Event` - событие, которое запускает `workflow` (`push`, `pull_request`, `merge`)

`Job` - набор шагов, выполняемых на некотором узле исполнителе с кодом в ответ на `Event`

`Runner`- исполнитель `Job`, можно сказать вJOBыватель.

`Step` - команда или действие например `dotnet test` или `actions/checkout@v4`

`Action` - готовый скрипт/плагин для переиспользования в `Step` (например `actions/checkout@v4`)

**Как это устроено внутри**

Gitea Actions состоит из трёх компонентов

1. `Gitea Server` - хранит workflow-файлы, управляет запуском 
2. `Runner` (`act_runner`) - вJOBыватель
3. `Act` - движок, который интерпретирует `workflow` и выполняет шаги `Step`

Gitea Actions совместим с Github Actions, но имеет различия с ним

* Путь к **Workflow**: **Github**: `.github/workflows/` **Gitea**: `.gitea/workflows/`
* Контекстные переменные: **Github**: `github.*` и **Gitea**: `gitea.*`
* Некоторые `actions` работают иначе и нужно сверять совместимость и тестировать. 

## Gitea Actions и Runner

Для Gitea 1.21 и выше actions включены по умолчанию. Если используется более старая версия, необходимо в `/data/gitea/conf/app.ini` добавить секцию:

```ini
[actions]
ENABLED = true
```

После этого перезапустить Gitea

**Далее необходимо получить токен для Runner**

* На уровне инстанса: `http://localhost:3000/admin/actions/runners`
* На уровне организации: `http://localhost:3000/<org>/settings/actions/runners`
* На уровне репозитория: `http://localhost:3000/<owner>/<repo>/settings/actions/runners`

Токен выглядит как случайная строка: `P2U1U0oB4XaRCi8azcngmPCLbRpUGapalhmddh23`

## Регистрация Runner

**Ручной способ**

`./act_runner register` - данный скрипт попросит параметры:

* URL инстанса Gitea (например, http://192.168.8.8:3000/) — не используй localhost или 127.0.0.1
* Токен инстанса
* Имя раннера (не обязательно)
* Метки раннера (не обязательно)

Не интерактивная регистрация в одну команду:

`./act_runner register --no-interactive --instance http://192.168.8.8:3000 --token <токен>`

**Docker Runner**

```bash
docker run -d \
  --name=gitea-runner \
  -e GITEA_INSTANCE_URL=http://gitea:3000 \
  -e GITEA_RUNNER_REGISTRATION_TOKEN=<токен> \
  -v /var/run/docker.sock:/var/run/docker.sock \
  gitea/act_runner:latest
```

* `GITEA_INSTANCE_URL` — адрес твоей Gitea.
* `GITEA_RUNNER_REGISTRATION_TOKEN` — токен, полученный на предыдущем шаге.
* `-v /var/run/docker.sock` — позволяет runner запускать контейнеры внутри Docker (нужно для изоляции шагов).
* После регистрации runner запустится автоматически

Внутри админки Gitea runner будет `online` 

## Структура и синтаксис workflow-файла

В каждом репозитории Workflow файлы свои собственные и находятся в `.gitea/workflows/`

Базовая структура YAML-файла:

```yaml
# Имя workflow (отображается в интерфейсе)
name: CI/CD Pipeline

# События, которые запускают workflow
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

# Переменные окружения (доступны во всех jobs)
env:
  DOTNET_VERSION: '9.0.x'

# Jobs — выполняются параллельно, если не указано needs
jobs:
  # Job 1: Тестирование
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code # По сути получение в runner кода проекта. 
        uses: actions/checkout@v4

      - name: Setup .NET # установка dotnet указанной в env версии.
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Restore dependencies # запуск конкретных команд
        run: dotnet restore

      - name: Run tests
        run: dotnet test --no-restore --verbosity normal

  # Job 2: Сборка (запускается только после успешного test)
  build:
    runs-on: ubuntu-latest
    needs: test
    steps:
      - name: Build
        run: dotnet build --configuration Release --no-restore
```

## Gitea-специфичные контекстные переменные

Вместо `github.*` в **Gitea Actions** используется `gitea.*`:

Переменная - Что содержит
`${{ gitea.event_name }}`	Тип события (push, pull_request и т.д.)
`${{ gitea.ref }}`	Ветка или тег (например, refs/heads/main)
`${{ gitea.sha }}`	Хеш коммита
`${{ gitea.repository }}`	Имя репозитория (owner/repo)
`${{ gitea.actor }}`	Имя пользователя, запустившего workflow
`${{ gitea.run_id }}`	Уникальный ID запуска
`${{ gitea.run_number }}`	Номер запуска (инкрементируется)
`${{ gitea.server_url }}`	URL Gitea-сервера
`${{ gitea.api_url }}`	URL API Gitea

## Секреты — безопасное хранение паролей и ключей

**Секреты** — это зашифрованные переменные, которые хранятся в **Gitea** и подставляются в **workflow** во время **выполнения**. Они нужны для:

* **Логинов** и **паролей** в **Docker Hub**.
* **SSH-ключей** для доступа к серверу.
* **API-токенов** для внешних сервисов.

**Важно**: секреты не видны в логах и не доступны через API после создания

Секреты можно создавать на трёх уровнях:

* **Репозиторий** — доступны только для этого репозитория.
* **Организация** — доступны для всех репозиториев организации.
* **Инстанс** — глобальные секреты для всех репозиториев (не поддерживается напрямую)

**Как создать секрет в Gitea?**

* Открой репозиторий в Gitea.
* Перейди в Settings → Secrets.
* Нажми Add Secret.
* Введи имя (например, DOCKER_USERNAME) и значение.

**Как использовать секрет в workflow?**

```yaml
steps:
  - name: Log in to Docker Hub
    run: echo "${{ secrets.DOCKER_PASSWORD }}" | docker login -u "${{ secrets.DOCKER_USERNAME }}" --password-stdin
```

Gitea автоматически подставит значения секретов в secrets контекст

**Правила именования секретов**

* Только буквы, цифры и подчёркивания.
* Не могут начинаться с `GITHUB_` или `GITEA_`.
* Не чувствительны к регистру.

## Логи и артефакты — как понять, что происходит

**Где смотреть логи**

Логи каждого запуска доступны в интерфейсе Gitea:

* Открой репозиторий.
* Перейди в `Actions`.
* Выбери конкретный запуск.
* Нажми на любой `job` — увидишь логи каждого шага.

**Что можно найти в логах**

* Успешно ли прошёл `dotnet restore`.
* Какие тесты упали (и почему).
* Ошибки сборки **Docker-образа**.
* Сообщения об ошибках деплоя.

**Включение подробных логов (step-debug)**

```yaml
env:
  ACTIONS_STEP_DEBUG: true
  ACTIONS_RUNNER_DEBUG: true
```

Это включит дополнительные логи для каждого шага.

**Артефакты — сохранение результатов сборки**

Артефакты — это файлы, которые сохраняются после выполнения workflow (например, результаты тестов, собранные .dll, логи). Их можно скачать через интерфейс Gitea.

Пример сохранения артефакта:

```yaml
- name: Upload test results
  uses: actions/upload-artifact@v4
  with:
    name: test-results
    path: ./TestResults/
```

## Gitea Actions vs GitLab CI — сравнение подходов

**Аспект** - Gitea Actions / GitLab CI
**Совместимость** - Совместим с GitHub Actions (синтаксис YAML) / Собственный синтаксис YAML
**Ресурсы** - Лёгкий (~512MB RAM) / Тяжёлый (~4GB RAM)
**Установка** - Простая, один контейнер / Сложнее, несколько компонентов
**Экосистема** - Меньше готовых actions / Огромная экосистема, множество готовых шаблонов
**Зрелость** - Моложе, могут быть баги / Зрелый, проверенный годами
**Интеграция** - Только Git + CI / «Всё в одном» (Git, CI/CD, реестр, мониторинг)
**Сложные пайплайны** - Ограничен / Глубокая поддержка
Вывод:

`Gitea Actions` — для соло-разработчика или малой команды: просто, дёшево, предсказуемо.
`GitLab CI` — для корпоративных сценариев с кучей интеграций: мощнее, но дороже и сложнее

## Где логи, Тони?

**Что можно получить**	Где / Как
**Статус каждого шага**: 	Интерфейс Actions → логи шагов
**Время выполнения каждого шага**: 	Интерфейс Actions → общее время job
**Ошибки компиляции**: 	Логи шага dotnet build
**Упавшие тесты**: 	Логи шага dotnet test
**Переменные окружения**: 	Добавь шаг run: env — выведет все переменные
**Содержимое файлов**: 	Добавь шаг run: cat path/to/file
**Секреты**: 	НЕ видны в логах (защищены)
**Артефакты**: 	Скачать через интерфейс Actions

## Практический пример — полный workflow для .NET-проекта

```yaml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  DOTNET_VERSION: '9.0.x'
  REGISTRY: docker.io
  IMAGE_NAME: myapp

jobs:
  # -------- Job 1: Тестирование --------
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Restore dependencies
        run: dotnet restore

      - name: Run tests
        run: dotnet test --no-restore --verbosity normal

      - name: Upload test results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: ./TestResults/

  # -------- Job 2: Сборка Docker-образа --------
  build:
    runs-on: ubuntu-latest
    needs: test
    if: github.ref == 'refs/heads/main'  # Только для main
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
```

## Docker-compose и деплой на сервер

**Установка Docker-compose** 

```bash
# Обновляем список пакетов
sudo apt update

# Устанавливаем Docker и плагин Compose
sudo apt install -y docker.io docker-compose-plugin
```

Для запуска сервиса из контейнера требуется написать `docker-compose.yml`:

```yaml
# ============================================================
# Версия формата Compose (используй 3.8 для новых фич)
# ============================================================
version: '3.8'

# ============================================================
# Описание сервисов (контейнеров)
# ============================================================
services:
  # -------- Веб-приложение (API) --------
  web:
    # Имя образа для скачивания или сборки
    image: myapp:latest

    # Пробрасываем порты: хост:контейнер
    # Порт 8080 на хосте → порт 8080 внутри контейнера (ASPNETCORE_URLS)
    ports:
      - "8080:8080"

    # Переменные окружения, передаваемые в контейнер
    environment:
      - ASPNETCORE_ENVIRONMENT=Production   # Режим работы приложения

    # Политика перезапуска: unless-stopped — не перезапускать, если остановлен вручную
    restart: unless-stopped

  # -------- База данных PostgreSQL --------
  postgres:
    image: postgres:15          # Официальный образ PostgreSQL 15

    # Переменные для настройки БД
    environment:
      - POSTGRES_USER=myapp     # Имя пользователя БД
      - POSTGRES_PASSWORD=mysecret  # Пароль (в реальности — секрет)

    # Тома для сохранения данных (чтобы не потерять при перезапуске)
    volumes:
      - pgdata:/var/lib/postgresql/data   # Именованный том pgdata

# ============================================================
# Описание томов (для хранения данных вне контейнера)
# ============================================================
volumes:
  pgdata:   # Том для PostgreSQL — данные сохраняются между запусками
```

Чтобы управлять запуском используются следующие команды:

```bash
# Запустить все сервисы в фоновом режиме
docker compose up -d

# Остановить и удалить контейнеры (тома остаются)
docker compose down

# Посмотреть логи всех сервисов
docker compose logs

# Перезапустить только веб-сервис (без остановки БД)
docker compose restart web
```

**Как должен выглядеть автодеплой с Docker Compose**

Схема простая:

* Gitea Actions собирает Docker-образ и пушит его в реестр (Docker Hub, GHCR или локальный).
* Gitea Actions подключается к серверу по SSH и выполняет команды:
* docker pull — скачать новый образ.
* docker compose up -d — перезапустить сервисы с новым образом.

**Пример workflow для Gitea Actions**

```yaml
# ============================================================
# Workflow: CI/CD с автодеплоем через Docker Compose
# ============================================================
name: Deploy with Docker Compose

on:
  push:
    branches: [main]   # Деплой только при пуше в main

env:
  REGISTRY: docker.io
  IMAGE_NAME: myapp
  SERVER_HOST: ${{ secrets.SERVER_HOST }}   # IP или домен сервера
  SERVER_USER: ${{ secrets.SERVER_USER }}   # Имя пользователя на сервере

jobs:
  # -------- Job 1: Тестирование --------
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '9.0.x'

      - name: Restore dependencies
        run: dotnet restore

      - name: Run tests
        run: dotnet test --no-restore --verbosity normal

  # -------- Job 2: Сборка и пуш образа --------
  build:
    runs-on: ubuntu-latest
    needs: test
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest

  # -------- Job 3: Автодеплой на сервер через SSH --------
  deploy:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Deploy via SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SERVER_SSH_KEY }}   # Приватный SSH-ключ
          script: |
            # Переходим в папку с проектом
            cd /opt/myapp

            # Скачиваем свежий образ
            docker pull ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest

            # Перезапускаем сервисы (только те, у которых изменился образ)
            docker compose up -d --no-deps --force-recreate web

            # Очищаем неиспользуемые образы
            docker image prune -f
```

**Что нужно настроить на сервере**

* Установить Docker и Docker Compose.
* Создать папку для проекта, например /opt/myapp, и положить туда docker-compose.yml.
* Сгенерировать SSH-ключ и добавить публичный ключ в ~/.ssh/authorized_keys на сервере.
* Добавить секреты в Gitea:
  * SERVER_HOST — IP или домен сервера.
  * SERVER_USER — имя пользователя (например, deploy).
  * SERVER_SSH_KEY — приватный SSH-ключ.
  * DOCKER_USERNAME и DOCKER_PASSWORD — для доступа к Docker Hub.

**Ограничения**

Для большой команды и корпоративной среды данный подход не является оптимальным как минимум по причине отсутствия возможности отката и передачи ssh ключа от прод сервера на откуп секретам Gitea, поэтому так делать не надо, но для соло и малых команд разработки - это просто и эффективно решает задачи, а что решает задачи - приносит деньги.

## Minikube — локальный Kubernetes

`Minikube` — локальный Kubernetes-кластер для разработки и тестирования.

Пример установки Minikube на x64 систему:

```bash
# ============================================================
# Установка Minikube
# ============================================================
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube

# ============================================================
# Запуск кластера (используем драйвер Docker)
# ============================================================
minikube start --driver=docker

# ============================================================
# Установка kubectl (инструмент управления Kubernetes)
# ============================================================
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install kubectl /usr/local/bin/kubectl
```

Каждый проект, развёрнутый в k8s состоит из 3-х манифестов:

```bash
k8s/
├── deployment.yaml    # Описание подов (контейнеров)
├── service.yaml       # Описание доступа к сервису
└── ingress.yaml       # Описание внешнего доступа (опционально)
```

Проекты и среды исполнения могут разделяться посредством `namespace` и проекты в разных `namespace` могут быть изолированы друг от друга, иметь разные переменные окружения и версии ПО.

```bash
# Создаём два namespace: test и prod
kubectl create namespace test
kubectl create namespace prod
```

Далее рассмотрим деплой по пушу в k8s из Gitea репозитория

`service.yaml` test среды:

```yaml
# ============================================================
# Service — определяет доступ к подам
# ============================================================
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
  namespace: test          # Принадлежит namespace test
spec:
  # ClusterIP — доступен только внутри кластера
  # Это безопасно для тестового окружения
  type: ClusterIP

  # Селектор — к каким подам направлять трафик
  selector:
    app: myapp             # Только поды с меткой app=myapp

  # Проброс портов
  ports:
    - port: 80             # Порт внутри кластера
      targetPort: 8080     # Порт внутри контейнера
```

`service.yaml` prod среды:

```yaml
# ============================================================
# Service для продакшена — доступен извне
# ============================================================
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
  namespace: prod          # Отдельный namespace для прода
spec:
  # LoadBalancer — создаёт внешний IP для доступа из интернета
  type: LoadBalancer

  selector:
    app: myapp             # Те же поды, но в другом namespace

  ports:
    - port: 80
      targetPort: 8080
```

Проверка:

```bash
# Для test-окружения — пробросить порт локально
kubectl port-forward service/myapp-service 8080:80 -n test

# Для prod — получить внешний IP
minikube service myapp-service -n prod --url
```

Чтобы Gitea могла деплоить в кластер изменения в контейнерах, требуется настроить доступ к кластеру, для этого необходимо получить Base64 строку параметров подключения: `kubectl config view --raw > kubeconfig` и полученное значение записать в переменную `KUBE_CONFIG_DATA` и написать следующий пайплайн:

```yaml
# ============================================================
# Имя workflow (отображается в интерфейсе Gitea)
# ============================================================
name: CI/CD Pipeline

# ============================================================
# Триггеры — когда запускать
# ============================================================
on:
  push:
    branches:
      - main          # Пуш в main → деплой в prod
      - develop       # Пуш в develop → деплой в test

# ============================================================
# Глобальные переменные окружения
# ============================================================
env:
  REGISTRY: docker.io               # Реестр Docker
  IMAGE_NAME: myapp                 # Имя образа

jobs:
  # -------- Job 1: Тестирование (общий для всех веток) --------
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '9.0.x'

      - name: Restore dependencies
        run: dotnet restore

      - name: Run tests
        run: dotnet test --no-restore --verbosity normal

      - name: Upload test results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: ./TestResults/

  # -------- Job 2: Сборка Docker-образа --------
  build:
    runs-on: ubuntu-latest
    needs: test
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

  # -------- Job 3: Деплой в test (только для develop) --------
  deploy-test:
    runs-on: ubuntu-latest
    needs: build
    # Запускается только для пуша в develop
    if: github.ref == 'refs/heads/develop'
    steps:
      # Восстанавливаем kubeconfig из секрета
      - name: Set kubeconfig
        run: echo "${{ secrets.KUBE_CONFIG_DATA }}" | base64 -d > kubeconfig

      # Обновляем образ в deployment и ждём завершения
      - name: Deploy to test namespace
        run: |
          export KUBECONFIG=kubeconfig
          kubectl set image deployment/myapp myapp=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }} -n test
          kubectl rollout status deployment/myapp -n test

  # -------- Job 4: Деплой в prod (только для main) --------
  deploy-release:
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Set kubeconfig
        run: echo "${{ secrets.KUBE_CONFIG_DATA }}" | base64 -d > kubeconfig

      - name: Deploy to prod namespace
        run: |
          export KUBECONFIG=kubeconfig
          kubectl set image deployment/myapp myapp=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }} -n prod
          kubectl rollout status deployment/myapp -n prod
```

После этого при изменении релизных версий контейнера он автоматически будет обновляться в запущенных подах. 

## Деплой с Helm (декларативный подход)

`Helm` — пакетный менеджер для Kubernetes. Он упаковывает манифесты в чарт (шаблонизированный набор YAML-файлов). Позволяет управлять версиями деплоя, откатами и настройками для разных сред.

Установка:

```bash
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
```

Более подробно тема сборки контейнеров, доставки, развёртывания со всеми конфигурационными файлами будет [рассмотрена](../../DevOps/Docker.md) в DevOps ветке репозитория
