# Управление проектами .sln .csproj 

`.sln` - файл решения, решение - совокупность проектов (`.csproj`), которые связаны между собой и взаимодействуют. Типичный сценарий: подключаемая `dll` библиотека `.csproj`, содержащая бизнес-логику и модель данных, фронтенд проект и бекенд проект, связность определяется решением, решение определяет порядок сборки и линковки. 

`.csproj` - содержит информацию о конкретном проекте: версия .Net, зависимости, устанавливаемые NuGet пакеты.

`.sln` - содержит информацию о входящих в решение проектах и настройки окружений сборки. Призван упрощать работу с многопроектными решениями (тонна ебаных микросервисов)

## структура проекта .csproj

```xml
<Project Sdk="Microsoft.NET.Sdk"> <!-- Определение типа проекта и настроек для него. .NET.Sdk - библиотека, .NET.Sdk.Web - веб приложение -->
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework> <!-- Версия платформы, на которой собирается проект -->
    <OutputType>Exe</OutputType> <!-- Формат выхода. Если Library - dll (по умолчанию, если не задан, будет либа), Exe - executable -->
    <Nullable>enable</Nullable> <!-- проверка, что зависимости удовлетворены, чтобы избежать NullReferenceException -->
    <ImplicitUsings>enable</ImplicitUsings> <!-- Авто-подключение стандартных глобальных компонент (using System/using System.Collections.Generic и др.) -->
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Newtonsoft.Json" Version="13.0.3" /> <!-- NuGet пакеты. Имя и версия -->
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="..\MyProject.Core\MyProject.Core.csproj" /> <!-- Ссылка на другие проекты -->
  </ItemGroup>
</Project>
```

## Сборка проекта

`dotnet build` - основная команда сборки проекта, она выполняет ряд более простых операций:

- `dotnet restore` - восстанавливает NuGet пакеты из .csproj ссылок. По сути проверяет не битые ли файлы, не удалены ли они и если что-то не соответствует тому, что в репозитории, приводит к виду из репозитория NuGet пакетов.
- Компиляция. - транслирует `.cs` файлы в `IL` - промежуточный байткод, который в последствие исполняет байт-код интерпретатор среды исполнения, который уже имеет оптимизации для компиляции в нативный машинный код, но первый прогон будет через `IL`
- Сборка - она же линковка и упаковка промежуточного кода в исполняемый файл для среды исполнения .Net Runtime. 

`dotnet publish` - подготовка к публикации. Ресторит и собирает проект

`dotnet run` - собирает и запускает приложение

`dotnet test` - собирает и запускает unit-тесты

## Package Reference

Управление зависимостями происходит через PackageReference секцию в .csproj файле

```xml
<ItemGroup>
  <PackageReference Include="Microsoft.EntityFrameworkCore" Version="9.0.0" />
  <PackageReference Include="Swashbuckle.AspNetCore" Version="6.5.0" />
</ItemGroup>
```

Версии указываются:
- Полностью: `Version="9.0.0"`
- Wildcard: `Version="9.*"` - будет использоваться самая новая версия в ветке 9-х версий

Можно так же создать файл `Directory.Packages.props`, где указать версии пакетов и в `.csproj` указывать только название пакета, а версиями управлять через этот файл.

## Работа с проектами и решениями

Типовая структура решения:

```bash
MyApp.sln
├── src/
│   ├── MyApp.Web/                 # Web API (.csproj)
│   ├── MyApp.Core/                # Бизнес-логика (.csproj)
│   └── MyApp.Infrastructure/      # Доступ к данным (.csproj)
└── tests/
    └── MyApp.Tests/               # Unit-тесты (.csproj)
```

Создание решения через CLI (command line interface):

```bash
# 1. Создаём решение
dotnet new sln -n MyApp

# 2. Создаём проекты
dotnet new webapi -n src/MyApp.Web
dotnet new classlib -n src/MyApp.Core
dotnet new classlib -n src/MyApp.Infrastructure
dotnet new xunit -n tests/MyApp.Tests

# 3. Добавляем проекты в решение
dotnet sln MyApp.sln add src/MyApp.Web/MyApp.Web.csproj
dotnet sln MyApp.sln add src/MyApp.Core/MyApp.Core.csproj
dotnet sln MyApp.sln add src/MyApp.Infrastructure/MyApp.Infrastructure.csproj
dotnet sln MyApp.sln add tests/MyApp.Tests/MyApp.Tests.csproj
```

После создания структуры, требуется связать проекты, делается это так:

```bash
# MyApp.Web зависит от MyApp.Core
dotnet add src/MyApp.Web/MyApp.Web.csproj reference src/MyApp.Core/MyApp.Core.csproj
```

либо вручную прописать в `.csproj`

```xml
<ItemGroup>
  <ProjectReference Include="..\MyApp.Core\MyApp.Core.csproj" />
</ItemGroup>
```

**Профили сборки**

В .Net предусмотрено два стандартных профиля сборки приложений: 
- `Debug` - профиль без оптимизаций и включающий в себя отладочную информацию (.pdb файлы). Во время разработки используется именно эта сборка 
- `Release` - профиль с оптимизациями, ограничениями отладочной информации, используется для деплоя приложения или доставки его конечным пользователям.

Поддерживается так же условная компиляция через символы:

```c#
#if DEBUG
    Console.WriteLine("Этот код выполняется только в Debug");
#endif

#if RELEASE
    Console.WriteLine("Этот код выполняется только в Release");
#endif
```

Настроить символы можно в конфигурации `.csproj`:

```xml
<PropertyGroup Condition="'$(Configuration)' == 'Debug'">
  <DefineConstants>DEBUG;TRACE</DefineConstants>
</PropertyGroup>
<PropertyGroup Condition="'$(Configuration)' == 'Release'">
  <DefineConstants>RELEASE;TRACE</DefineConstants>
</PropertyGroup>
```

## Практический пример

**Консольное приложение**

```bash
# Создаём проект
dotnet new console -n MyConsoleApp

# Запускаем
cd MyConsoleApp
dotnet run
```

`.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net9.0</TargetFramework>
  </PropertyGroup>
</Project>
```

**Web-API**

```bash
# Создаём решение
dotnet new sln -n MyApp

# Создаём проекты
dotnet new webapi -n src/MyApp.Web
dotnet new classlib -n src/MyApp.Core
dotnet new xunit -n tests/MyApp.Tests

# Добавляем в решение
dotnet sln MyApp.sln add src/MyApp.Web/MyApp.Web.csproj
dotnet sln MyApp.sln add src/MyApp.Core/MyApp.Core.csproj
dotnet sln MyApp.sln add tests/MyApp.Tests/MyApp.Tests.csproj

# Добавляем ссылки
dotnet add src/MyApp.Web/MyApp.Web.csproj reference src/MyApp.Core/MyApp.Core.csproj
dotnet add tests/MyApp.Tests/MyApp.Tests.csproj reference src/MyApp.Core/MyApp.Core.csproj
```

И получаем `Core` - для бизнес логики и моделей данных, тесты и эндпоинт в виде `webApi`. К этому всему сделать фронтенд уже не составляет проблемы, добавив `WebAssembly` через `BlazorWASM` и использовать уже готовую бизнес-логику. 

## Контрольные вопросы

**Чем отличается .sln от .csproj?**

`.sln` содержит информацию о решении - многопроектной системе, а `.csproj` о конкретном проекте, который может быть самодостаточным, а может быть и частью большой системы. `.sln` содержит информацию о сборке, входящих в него проектах, а `.csproj` содержит информацию о зависимостях, ссылках, целевой платформе, выходном файле и т.п.

**Какие три основных элемента обязательно должны быть в .csproj?**

sdk, output и платформа

**Какая команда создаёт новое решение?**

`dotnet new sln -n Name`

**Как добавить существующий проект в решение через CLI?**

`dotnet sln Name add link/to/csproj`

**Чем отличается dotnet build от dotnet publish?**

publish собирает для деплоя, build не обязательно

**Как добавить ссылку на NuGet-пакет в .csproj?**

Вручную указать `PackageReference` в `.csproj` или `dotnet add package`

**Как добавить ссылку на другой проект в том же решении?**

Вручную указать `ItemReference` в `.csproj` или `dotnet add [ToWho] reference [fromWho]`

**Как включить условную компиляцию для Debug и Release?**

Создать символы в конфигурции `.csproj` через `DefineConstant` и после использовать `#if символ`
